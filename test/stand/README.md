# Сетевой стенд (Linux, Docker)

Один `docker run --rm --privileged` контейнер, внутри network namespaces:
`client` (где работает vpnsplit) - `isp` (NAT) - `inet` (1.1.1.1 с DNS, интернет),
`corp` (WireGuard-сервер wgcorp, 10.10.0.0/16, DNS corp.example),
`home` (WireGuard-сервер wghome, NAT в inet). Адреса 203.0.113.10-13 есть в
inet, corp и home, и каждый отвечает по HTTP своим именем: `curl` показывает путь пакета.

Запуск с Windows (хост сеть не меняется, всё внутри контейнера):

```
powershell -File test\stand\run.ps1              # все сценарии
powershell -File test\stand\run.ps1 -Only S3     # один сценарий
powershell -File test\stand\run.ps1 -HomeVariant b
```

`run.ps1` собирает Linux-бинарь (`GOOS=linux go build -tags vpnsplit_stand`: тег включает только в стенде
хук медленного удаления для S8, он читает файл `/tmp/stand/slow-del`), один раз собирает образ
`vpnsplit-stand` (alpine + iproute2, wireguard-tools, dnsmasq, python3, iptables;
нужен интернет) и запускает `stand.sh`. Нужно ядро с модулем wireguard (Docker
Desktop / WSL2 его имеет). Код возврата 1, если любая проверка не прошла.

Сценарии этапов 1-2 (маршруты проверяются `ip route get` и `curl`, чистота - сравнением
таблицы маршрутов и правил client со снимком до запуска):

| id | что |
|----|-----|
| S0 | без vpnsplit всё идёт в inet |
| S1 | `run`, правила применены (corp / direct / остальное), SIGTERM, таблица = снимок |
| S2 | то же для SIGINT и SIGHUP |
| S3 | `run`, `kill -9`, остались маршруты, повторный `run` (или `reset`) убирает их, SIGTERM, таблица = снимок |
| S4 | `apply` (persistent) оставляет маршруты, `run` забирает их, SIGTERM, чисто |
| S5 | вторая копия (`run`, `reset`, `apply`) при живой первой ничего не меняет |
| S6 | меню на псевдотерминале закрывается `q`, Ctrl+C, SIGTERM, SIGHUP, закрытием терминала: чисто; меню второй копии только показывает |
| S7 | меню при persistent-журнале (после `apply`): `q` выходит, ничего не снимая и сообщая об этом; затем `t` (забрать в сессию) и `q` снимают всё, итог записан в `last-session.log` |
| S8 | медленное удаление маршрута (хук стенда, 8 с на маршрут): второй SIGINT во время снятия завершает процесс сразу (код 130), журнал хранит остаток, следующий запуск доделывает; SIGTERM при медленном снятии: выход через ~4,5 с от сигнала с ненулевым кодом, остаток в журнале, итог в `last-session.log` и в `status` |
| S9 | домашний VPN переподключается под тем же именем (`ip link del wghome` + создание заново, новый индекс): за <= 5 с маршруты восстановлены, curl снова идёт в home; S9b - VPN отсутствует 3 с; S9c - то же для корпоративного |
| S10 | 2000 корпоративных префиксов (`vpnsplit import`): apply быстрее 15 с, в таблице 2000+ маршрутов с protocol 247 (в варианте b все в таблице 247 и одно правило `lookup 247`, а не правило на префикс), журнал записан целиком, повторных apply нет, очистка по SIGTERM укладывается в 4,5 с |
| S11 | корпоративный адаптер удалён (`ip link del wgcorp`): трафик к корпоративным адресам не уходит в eth0 мимо домашнего VPN (маршрут не в eth0, `tcpdump` на eth0 клиента: 0 пакетов к этим адресам, `curl` отвечает home, не inet). В варианте b сначала контроль: старое правило `to <префикс> lookup main` в том же положении протекает (пакеты на eth0 видны), так что проверка способна увидеть утечку |
| S12 | корпоративная сеть 198.18.0.0/16 накрывает адреса серверов обоих VPN (198.18.1.2 и 198.18.2.2): она не применяется (предупреждение называет оба адреса), серверы идут через eth0, оба туннеля живы (свежий handshake). В вариантах b и c сценарий сам ставит host-маршруты на серверы через eth0, как клиент, который их закрепляет |
| S13 | оба адаптера переподключаются под теми же именами несколько раз (новые индексы, один раз с паузой 2.5 с); `vpnsplit diff` во время сеанса знает свои маршруты («ours»), чужих не видит; после выхода `ip route show table all` + `ip rule` равны снимку, в выводе и в `last-session.log` «Restored to the state before the start», файл `snapshot.json` удалён |
| S14 | SIGTERM при медленных удалениях (хук `slow-del`): остаток в журнале, снимок остаётся; следующий старт доделывает и пишет «state before the earlier run: Restored …»; после выхода таблица равна снимку |
| S15 | маршруты старой версии (metric 1, без метки протокола) для префиксов из правил и её журнал в профиле (`~/.config/vpnsplit/state.json`): сеанс забирает их, заменяет и снимает; журнал уходит из профиля; таблица равна снимку |
| S16 | «клиент» добавляет маршрут посреди сеанса (`192.0.2.0/24` через wgcorp): он остаётся, `diff` и вывод при выходе называют его «not set by vpnsplit» и адаптер, «Differences left: 1»; маршрут с нашей меткой 247, которого нет в журнале, на адаптере eth0 (не клиентском) снимается; после удаления клиентского маршрута таблица равна снимку |
| S17 | «клиент» после снимка ставит маршрут с ключом нашего плана (`203.0.113.11/32` через wgcorp, proto boot; в варианте b при нашем маршруте в таблице 247 метрика 1, в a и c метрика 7; iproute2 не печатает `proto boot`, поэтому ищется метрика): после выхода он остаётся, `diff` и вывод называют его «not set by vpnsplit», нашим он не назван; наши маршруты сняты |
| S18 | маршрут с нашей меткой 247, которого нет в журнале, на адаптере распознанного VPN-клиента (dummy `happ0`, клиент Happ): не удаляется, вывод называет его и причину («VPN client») |

`-HomeVariant` - как ведёт себя клиент домашнего VPN (проходят все сценарии всех вариантов):

- `a` (по умолчанию) - клиент ничего не делает, кроме host-маршрутов до серверов VPN через физический шлюз; "остальное" в домашний VPN направляет сам vpnsplit (0/1 + 128/1 в main);
- `b` - как sing-box: сокеты туннелей помечены fwmark 2022, `ip rule pref 9000 not fwmark 2022 lookup 2022`, в таблице 2022 default через wghome. Main до правила не доходит, поэтому vpnsplit кладёт маршруты corp и direct в таблицу 247 (protocol 247) и добавляет одно правило `ip rule pref 5000 lookup 247` без селекторов (если в таблице 247 маршрута нет, пакет идёт дальше, к правилу клиента), и не добавляет 0/1 + 128/1;
- `c` - как wg-quick: fwmark 51820, `not fwmark 51820 lookup 51820` и перед ним `lookup main suppress_prefixlength 0`. Маршруты из main видны без правил, vpnsplit их не добавляет и 0/1 + 128/1 тоже.

В b и c "остальное" идёт в home и без vpnsplit (S0 это проверяет).

Заметки: split DNS на Linux работает только с systemd-resolved; в контейнере его нет,
поэтому DNS-часть (NRPT/resolver-записи) здесь no-op. Корпоративные домены
резолвятся через `corp-dns` и превращаются в маршруты.

Сценарии этапа 3 (DNS, IPv6, «Остальной трафик»). В контейнере нет systemd-resolved, поэтому на время этих
сценариев в `/usr/sbin/resolvectl` ставится заглушка (`fake-resolvectl.sh`, состояние линков в `/tmp/stand/resolved`):
vpnsplit спрашивает и меняет её так же, как настоящий resolvectl, а «NetworkManager затёр домен» играется записью в файл.
Захват пакетов - `tcpdump` на `eth0`, `wghome`, `wgcorp` клиента; на DNS проверяется, что вопросы идут только куда нужно.

| id | что |
|----|-----|
| S19 | пути DNS: имена «напрямую» спрашиваются у DNS провайдера (`1.1.1.1`, маршрут /32 через eth0 и шлюз, метка 247), корп. имена у корп. DNS (маршрут /32 через wgcorp), в домашний VPN (`wghome`) не уходит ни одного DNS-пакета; ответ из 198.18.0.0/15 (`fake.example` -> 198.19.5.5) отброшен и назван в выводе, маршрута для него нет; зоны direct-имён записаны на линк eth0 (`~direct.example`, свои домены линка сохранены), DNS самого eth0 не тронут; после выхода таблица = снимок, DNS и домены линков как до запуска (удаление записей одного линка идёт последовательно: чтение-изменение-запись домена линка не должны затирать друг друга) |
| S20 | `~.` на линке домашнего VPN (остальные имена - к его DNS), корп. зона на линке wgcorp, запись в журнале; домен на линке стирают («NetworkManager»): цикл `run` возвращает его за <= 45 с, запись в журнале одна; после выхода линки как до запуска |
| S21 | у домашнего VPN есть глобальный IPv6 (2001:db8:77::/64) и хост только в нём (2001:db8:ff::10): в варианте a `::/1` и `8000::/1` через wghome с меткой 247, `curl -6` отвечает home, `status` об этом говорит; в b и c IPv6 забирает сам клиент (его правила, `ip -6 rule` читается), своих половин нет; `tcpdump` на `wghome` видит IPv6-пакеты к хосту, на `eth0` их нет; после выхода таблицы v4 и v6 + правила = снимок. S21b: у домашнего VPN нет IPv6, у eth0 есть: `status` заметно сообщает «IPv6 goes past the home VPN», IPv6-маршрутов нет |
| S22 | «Остальной трафик» = напрямую: `0/1` + `128/1` через eth0 и шлюз, правило `--home` уводит в wghome, корп. - в wgcorp; правило `--direct` не принимается («no meaning»); `tcpdump`: пакеты к «остальному» адресу идут по eth0 и не заходят в wghome (контроль: захват видит пакеты к `--home` адресу); NRPT/`~.` для домашнего VPN нет; `rules` показывает только нужные виды |
| S23 | «Не трогать»: правила corp и direct применены, своих `0/1` + `128/1` и DNS «остального» нет, остальное - как решил клиент (в варианте a - eth0, в b и c - home) |
| S24 | у провайдера в списке DNS есть DNS домашнего VPN (`1.1.1.1 10.201.0.1`): /32 до него не ставится, в выводе предупреждение, direct-имена спрашиваются у второго сервера (`tcpdump` на eth0), зона direct-имени на eth0; после выхода всё как до запуска |
| S25 | чужая `~.` уже стоит на линке домашнего VPN: она остаётся, в журнал не попадает, корп. зона ставится как обычно; повторный apply (по изменённому правилу) не пишет «=» заново, не сбрасывает кэш DNS (счётчик `flush` в журнале вызовов заглушки) и не трогает линк; после выхода чужая `~.` на месте |
| S26 | (только b и c) у домашнего VPN есть v6, его клиент забрал правилами только v4, у eth0 есть v6: `status` заметно сообщает «!!! IPv6 goes past the home VPN: its client sends only IPv4 ...», своих IPv6-маршрутов нет, v6-таблица после выхода = снимок. В варианте a сценарий пропускается (половины v6 свои, S21) |
| S27 | `resolvectl` не отвечает на чтение (режим `fail` заглушки): DNS-записей не планируется, домены/серверы линков не тронуты, в журнале записей нет; затем записи сделаны, чтение ломается к выходу - записи остаются в журнале и на линке, `reset` снимает их, когда resolvectl снова отвечает |

Настоящий systemd-resolved в контейнер не ставится: ему нужен systemd как PID 1 и D-Bus, а контейнер стенда запускает `bash stand.sh`. Поэтому проверка, что «остальной» DNS реально уходит на домашний сервер, сделана на уровне записей (`~.` на линке и вызовы заглушки), а не по пакетам. Это ограничение стенда.

Не покрыто стендом: Windows-часть (NRPT `.`, Teredo/6to4/ISATAP - проверена только юнит-тестами с фейковым бэкендом),
macOS (DNS «остального» не делается: `/etc/resolver` не умеет «.»).

Сценарии этапа 4 (детект и предупреждения). Детект только читает: каждый сценарий ставит «клиента» в
состояние с находкой, смотрит, что `vpnsplit status` печатает в блоке `diagnostics:` (строки
`  [info|warn|danger] КОД: текст` и `      -> совет`), и проверяет, что `status` ничего не изменил в таблице
(а там, где идёт сеанс `run`, что выход возвращает таблицу к снимку).

| id | что |
|----|-----|
| S28 | в обычной обстановке стенда нет ни warn, ни danger; в вариантах b и c домашний клиент (таблица политики, default через wghome) даёт только заметку `WG_FULL_TUNNEL` со словами «policy table»; собственная сеть адаптера (`10.200.0.0/24 dev wgcorp`) заметкой `CORP_ONLINK` не считается |
| S29 | домашний WireGuard с AllowedIPs 0/0: `WG_FULL_TUNNEL` (info); в варианте a клиент ставит `0/1` и `128/1` через wghome (маршруты клиента, без метки 247); третий WireGuard `wg9` с полным туннелем - warn |
| S30 | корп. VPN в полном туннеле: `0/1` + `128/1` через wgcorp, а также `default` через wgcorp с метрикой лучше, чем у eth0, - `CORP_FULL_TUNNEL` (warn); default хуже по метрике, чем у eth0, находкой не считается |

| S34 | корп. маршрут без next hop (клиент добавил `10.30.0.0/16 dev wgcorp`): план работает (`ip route get` без `via`, curl идёт в corp), `CORP_ONLINK` (info) |

Не покрыто стендом (только юнит-тесты на чистых функциях детекторов): WinINET и `scutil --proxy`/gsettings
